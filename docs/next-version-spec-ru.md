# Спецификация Quillgrain 0.1.0rc5

Статус: проект следующего релиза. Дата: 15 ноября 2026 года.
`0.1.0rc5` — предлагаемое обозначение после текущего `0.1.0rc4`.

Следующая версия должна сделать Quillgrain надёжным инструментом письма и
целевой редактуры в агенте. Пользователь получает переносимый skill с проверенным
контекстом, понимает, какой голос выбран, сохраняет исходник при правке и видит
фактическое покрытие проверок. Ink Duel получает готовый протокол исследования
самостоятельных художественных сцен: короткую сессию, понятное происхождение
текстов и корректный разбор даже незавершённого голосования.

В релиз выбраны **14 задач из 37 открытых ишью**. Приоритет отдан дефектам
готового skill, сохранности замысла при редактуре и последним решениям владельца
о следующем опыте. Подготовка протокола входит в объём версии; запуск реального
опыта и подтверждение качества конкретного голоса требуют отдельных результатов.

## Границы версии

Движок владеет контрактами, экспортом, общими инструкциями skill, проверками
и локальным клиентом оценки. Литературные предпочтения остаются в data packs.
Scriptorium сохраняет ответственность за измерения.

В версию не входят публикация GitHub Pages, сетевой сбор источников, новый
модельный сервис, изменение потребительских проектов, автоматическое обновление
установленных личных skills и продвижение правил из комментариев. Существующие
игры, сырые ответы, ключи, оценки и контексты сохраняют исходный смысл.

## Надёжный экспорт и выбор skill

### Проверка перед записью

Для #34 экспорт связанного skill и `skill install --bundle` используют один
контракт. До публикации каталога проверяются целостность context/lock, соответствие
целевого агента фактическому host, `retrieval` и `approved_model_hosts`.
Неподходящий host не переименовывается; разрешения не расширяются.

Ошибка оставляет конечный каталог несозданным. Проверка готового результата
охватывает `codex` и `claude`: разрешённый совпадающий host, несовпадение,
запрет host, повреждение context и несовпадающий lock. Используется существующая
политика создания нового каталога и транзакционной публикации.

### Имена и сосуществование

Для #35–36 предлагается следующий единый контракт:

- Общий skill по умолчанию называется `quillgrain`.
- Связанный skill получает имя `quillgrain-<voice-slug>`. Slug выводится из
  идентичности выбранного pack; если корректное имя получить нельзя, требуется
  явное `--skill-name`. Этот параметр одинаково действует в build и install.
- Имя проверяется по поддерживаемому формату Agent Skills. Папка, `name`,
  примеры вызова и UI metadata согласованы. Описания различают общий инструмент
  и выбранный голос; доступные metadata показывают версию и источник контекста.
- `--out` сохраняет смысл **точного конечного пути**. Его последнее имя должно
  совпасть с выбранным именем skill; иначе операция завершается до записи.
  При `--project` каталог строится из корня skills выбранного агента и имени.
- Перед успехом валидируется сгенерированное дерево: обязательные поля,
  локальные ссылки и наличие указанных ресурсов. Произвольный код из входного
  bundle не копируется и не исполняется.

Известные совпадения проверяются в целевом проекте и доступных стандартных
пользовательских расположениях. Диагностика сообщает проверенные расположения
и различия профилей; она не обещает обнаружить все возможные конфигурации.
Весь диск не сканируется, чужие skills не изменяются. Автоматический выбор
сохраняется, а явный выбор другого голоса имеет приоритет над встроенным.

Старые установленные папки не переименовываются. Документация описывает переход
через новую установку и отдельно — проверенное поведение Codex и Claude Code.
Нельзя обещать им одинаковое разрешение совпадений по одному лишь имени.

### Проверка после переноса

Для #37 движок поставляет собственный stdlib-помощник, общий для экспортируемых
skills. Он принимает выбранные context, lock и фактический host, проверяет
поддерживаемую версию, digest, бюджет и применимые семантические инварианты,
согласованность lock и разрешения. Вывод — компактные metadata либо проверенный
`prompt_payload`. Набор реально выполненных проверок обозначается явно.

Общая переносимая часть контракта используется и движком; общие синтетические
векторы препятствуют расхождению реализаций. Если полная JSON Schema проверяется
только движком, помощник прямо обозначает эту границу. Неизвестная версия,
повреждение, неподходящий host и запрещённый доступ завершаются отказом.

Приёмка переносит только папку skill и делает исходные engine, pack и export
недоступными. С установленным Python проверка продолжает работать без зависимостей
и сетевых запросов. При недоступном исполнении действует честный `NOT_RUN`.
Успех digest-проверки не является проверкой издателя или качества голоса.

## Целевая редактура и покрытие проверок

### Работа с исходным текстом

Общие инструкции #33 определяют по запросу одно из трёх действий: создать новый
текст, отредактировать существующий или переписать свободнее. Корректура двух
фраз не разрешает перестроить статью. Запрос черновика не запускает обязательную
полировку.

При редактуре исходник сохраняется отдельно. Ассистент определяет конкретный
дефект и меняет необходимый участок, сохраняя факты, степень уверенности,
говорящего, исход сцены и численные ограничения. Значимые смысловые изменения
обозначаются владельцу. После правки проверяется итоговый текст; работа
останавливается после выполнения запроса. Квоты сокращения, обязательные
многократные проходы и скрытые дополнительные модельные вызовы не вводятся.

Инструкции живут в исходном skill движка и доходят до всех вновь создаваемых
производных пакетов. Приёмочные сценарии: новая сцена, чистка двух оборотов,
перестройка статьи и черновик без полировки. Сохранность исходника и границы
правки проверяются по артефактам. В Ink Duel редакторский результат является
отдельным условием с отдельными затратами; сырой writer output не заменяется.

### Выбор исполнимых проверок

Для #39 перед `qg check` определяется, есть ли применимые исполнимые правила.
Контекст только с `human_review` ведёт к редакторскому чтению без обязательного
пустого технического прохода. Смешанный контекст запускает релевантные проверки
и различает выполненное, пропущенное и недоступное. Неизвестные character spans
не превращаются в успешную проверку реплик персонажа.

Явный диапазон слов всегда проверяется существующим `qg-words/v1`, включая
бюджеты частей и суммы. Это отдельное ограничение даже у полностью редакторского
профиля. По прямому запросу остаётся доступен технический аудит. Ни нулевой exit,
ни отсутствие findings не означают «стиль проверен».

### Редакторский список

Для #32 добавляется opt-in экспорт из существующей команды `qg check`:
предлагаемые параметры `--review-json NEW_FILE` и `--review-md NEW_FILE`.
Это явный запрос списка; он допустим и для полностью редакторского контекста.
Базовый `quillgrain.check-report/v1` и его значения сохраняются.

Новый `quillgrain.editorial-review/v1` содержит build ID контекста, digest
черновика и пункты из уже отобранных `rules_applied` с `enforcement=human_review`.
Для пункта сохраняются ID, исходная инструкция, язык, register, tags, channel,
character scope и начальный статус `NOT_REVIEWED`. Выбор языка/регистра/тегов
берётся из проверенного контекста. Неизвестная применимость к конкретному
персонажу обозначается явно. Отброшенные правила в список не возвращаются.

Повторный экспорт одинаковых входов воспроизводим. Markdown — представление
того же списка. Движок не придумывает новые редакторские требования, не ставит
человеческим пунктам PASS и не запускает модель. Список с содержимым pack
выводится локально по явному запросу.

Reviewer сначала читает целый текст. Замечания хранятся отдельно от исходника
и списка, с привязкой к пункту и участку текста. Для заметки документируются
категория, контекст, основание и объяснение потери: факт/brief, языковая норма,
регистр/аудитория/говорящий либо вкус. Допустимая альтернатива не объявляется
исправлением ошибки; утверждение о современной норме требует подходящего
современного источника. Отсутствие решения сохраняется как неизвестность.

## Проверка поведения в агенте и качества новых правил

### Приёмка skill

Для #38 создаётся компактный версионированный набор сценариев. Три исходных
семейства: создание сцены с выбранным голосом и объёмом; ограниченная правка
готового текста; работа с переносимым skill без установленного движка.
Дополнительно проверяются явный и автоматический вызов, неподходящий запрос,
прямо выбранный другой голос, язык/регистр, отсутствующий pack и запрещённый host.
Каждое сочетание параметров не становится отдельным обязательным опытом.

Запись результата фиксирует наблюдаемые действия: выбранные skill и context,
исполненный помощник, сохранённый исходник, итог и проверку бюджета либо
конкретный отказ. Фиксируются поверхность агента, доступная версия модели,
effort, инструменты и ограничения изоляции. Неизвестные значения не угадываются.

Качество маршрутизации, механическое выполнение и качество прозы оцениваются
отдельно. Для вывода о пользе профиля предусмотрены сопоставления без skill,
с краткой обычной инструкцией и с полным skill при одинаковом задании.
Результат другого интерфейса не подтверждает работу текущего.

Готовность к письму в обоих агентах требует фактически выполненной приёмки
на каждой заявленной поверхности. Если поверхность недоступна, её статус
остаётся `NOT_RUN`; общий успех не подменяет этот пробел. Обычный CI использует
синтетические данные и не вызывает платные модели. Новые реальные прогоны
выполняются только в рамках отдельно разрешённой проверки.

### Исправить или сохранить

Для #40 достаточно протокола и оригинальных синтетических fixtures; новый
runner и новая игра не нужны. Для каждого уточняемого правила задаются случай
необходимого вмешательства, близкий случай сохранения того же приёма, смысловая
граница, допустимые альтернативы и неопределённые решения.

Начальный набор охватывает нужный термин и пустую служебную конструкцию;
понятное сокращение и непрозрачный акроним; стандартную идиому, случайную порчу
и заданную игровую переделку. Ожидания описывают смысловые свойства, без
единственного эталонного предложения. Сохранение уместной формы — успешный исход.

Отдельно учитываются нарушение смысла, лишнее вмешательство и допустимая
вариативность. Кандидат сравнивается с заранее выбранной прежней редакцией при
одинаковых условиях; попытки сохраняются. Настройка использует development-набор,
последующая проверка — новый материал после фиксации кандидата. Варианты из одного
сценария не считаются независимыми доказательствами. Измерения остаются задачей
Scriptorium; литературное решение — задачей reviewer.

## Следующая ИнкДуэль

### Бюджет и экран

Для #27–28 используется существующая реализация quick-v1 с проверкой готового
клиента. Seed, бюджет, исходники и пары фиксируются до генерации и просмотра
результатов. По умолчанию — не более 30 дуэлей, допустима меньшая сессия.
Один source ID и одно нормализованное содержимое появляются ровно один раз.
Для нового задания единицей становится исходный факт-пакет.

Каждый раунд показывает два разных условия. Дополнительные условия не создают
дополнительные обязательные раунды. Выравниваются показы, стороны и категории
в пределах бюджета; полное покрытие всех пар не требуется. Невыполнимые заданные
квоты дают явную диагностику. Доступный сокращённый план показывает фактическое
число сравнений до начала; повтором источников недостаток не компенсируется.
Разные отрывки одного произведения учитываются как зависимые наблюдения.

На экране два читаемых текста, под каждым отдельное необязательное поле
«Что здесь удачно или мешает?». Единственная обязательная операция — одна из
ровно пяти оценок:

| Значение | Подпись |
| --- | --- |
| `left_strong` | ← Сильно лучше |
| `left_slight` | ← Чуть лучше |
| `tie` | Равно |
| `right_slight` | Чуть лучше → |
| `right_strong` | Сильно лучше → |

Оценки по умолчанию нет; отсутствие ответа отлично от равенства. Голос сохраняет
раунд и переводит дальше без обязательного подтверждения. Комментарии связаны
с ID карточек, переживают reload и импорт/экспорт. Клавиши 1–5 не голосуют во
время ввода текста. Проверяются двойной commit, возврат к сохранённому раунду,
фокус и узкий экран. Служебные действия находятся в компактном меню.

Совпадающие тексты не регенерируются ради различия. Их результат учитывается
как неразличимый, без исключительной победы условия. Шкала порядковая: сильная
победа не имеет удвоенного веса. Старые оценки не превращаются в общую оценку
или выдуманную силу предпочтения.

### Тип задания и происхождение

Для #30–31 текущего обязательного `source_text` в quick-sources/v1 недостаточно:
он описывает переработку готовой прозы. Новая сцена по факт-пакету получает
явный новый контракт, без фиктивного исходного отрывка.

Предлагается семейство `duel.quick-*/v2` для новых кампаний и
`duel.partial-report/v2` для расширенного отчёта. Изменённые структуры
источников, плана, слепого bundle и ключа получают новые версии; совместимые
структуры ответа могут сохранять v1 только при явно проверенной совместимости.
Существующие v1-файлы не меняют определения. Читатели выбирают обработчик по
версии и отклоняют неподдерживаемую версию.

В плане и закрытом ключе явно фиксируются:

| Поле | Смысл |
| --- | --- |
| `task_kind` | `rewrite`, `continuation` или `new_scene`; для старых данных без поля — `UNKNOWN` |
| Идентичность входа | ID и hash исходника либо канонического факт-пакета, work group и происхождение |
| Материал задания | Исходный отрывок, контекст продолжения либо факт-пакет новой сцены согласно типу |
| Происхождение карточки | Неизменённый источник или модельный ответ; профиль инструкций не является автором-человеком |
| Участие ORIGINAL | Наличие ORIGINAL в дизайне и фактическое число его показов, выведенное из mapping |
| Условия | Модель, reasoning, pack/base/version/digest, примеры, brief и границы независимости запросов |
| Пригодность материала | Проверка прав и смысла с отдельной локальной записью основания и разрешённых применений |

В слепой bundle попадает только безопасное пояснение типа задания и роли
источника, без соответствия карточек условиям, ключа и приватных locators.
До первого голоса участник видит, сравниваются ли переработки или новые сцены,
и участвуют ли оригиналы. Дополнительный обязательный шаг не появляется.
После завершения или явной остановки раскрываются реальные условия и версии.

ORIGINAL допустим только при наличии неизменённого исходного текста, с проверкой
совпадения. Наличие литературного источника на входе не означает его показа.
Само обозначение ORIGINAL не доказывает человеческое авторство: известный
статус производства текста хранится отдельно. Для новой сцены без готовой прозы
ORIGINAL не добавляется автоматически. Старые недостающие сведения остаются
неизвестными; их нельзя восстанавливать по жанру или имени профиля.

### Материал художественного пилота

Следующий план #31 проверяет создание самостоятельной сцены. Общий для условий
факт-пакет содержит действующих лиц и отношения, доступные им знания,
действие/конфликт, необходимые факты и исход либо границу остановки. Стиль
и авторские примеры передаются отдельно. Концепт игрового мира не обозначается
готовой сценой; заданный замысел не заменяется новым сюжетом ради эффекта.

Объём выбирается под ход сцены и фиксируется численно до генерации. Около ста
слов не является универсальной нормой. Контрольный writer добросовестно выполняет
то же задание; модель, reasoning, ограничения и независимость контекстов
сопоставимы либо явно отмечены как различающиеся факторы. Для вывода об улучшении
версии в условия включается конкретный предыдущий снимок.

План до запуска содержит вопрос опыта, task kind, разрешённый материал,
факт-пакеты, объём, условия, пары, seed, бюджет, ограничения и отдельные
development/reserve группы. Разделение с референсами проверяется на уровне
произведения. Известный разобранный материал не становится новым holdout.
Знакомство модели с классикой отмечается как ограничение.

Сохраняется общий принцип [#19](https://github.com/drevendev/Quillgrain/issues/19):
смысловые данные не являются готовыми фразами для вставки. Статус замысла
отделяется от грамматической формы; прямое описание концепции не требует
повторять «мог бы», а настоящая условность сохраняется. Новый prompt получает
новый digest; старые ответы не переоцениваются как результаты нового протокола.

### Остановка и интерпретация

Для #29 явное «Закончить и разобрать имеющееся» завершает активное голосование
и разрешает раскрытие. Частичный результат имеет статус `PARTIAL` с причиной
`STOPPED_BY_OWNER`. Draft сохраняется отдельно и не входит в знаменатели.
Проверяются digest сессии, исходного файла ответов и mapping; повреждённый импорт
не меняет текущий прогресс.

Отчёт показывает planned/committed, число разных исходников и произведений,
повторы, категории, показы каждого условия слева/справа и прямые встречи с `n`.
Нет наблюдений — неизвестность. Малые неравные выборки с разными соперниками
не создают турнирную таблицу. Качество, похожесть и узнавание в исторических
форматах остаются разными измерениями; без метаданных источник зависимости
остаётся неизвестным.

Уточнения от 15 ноября входят в обязательную приёмку:

- Относительный победитель может не нравиться участнику. Без отдельного
  свидетельства абсолютная удовлетворённость остаётся `UNKNOWN`.
- Исходный голос сохраняет счёт. Дословный комментарий, наличие указанной
  формулировки, редакторская интерпретация и гипотеза причины различаются.
- Одинаковая заметка на двух карточках не становится двумя независимыми
  дефектами. Наличие слова и в победителе, и в проигравшем не даёт общего запрета.
- Тип задания, жанр и сила предпочтения сопровождаются фактическим `n`.
  Победа на переработке не доказывает пользу на новых сценах или точность канона.

Для аналитики не добавляется шестая обязательная оценка. Сырые комментарии
и привязки сохраняются локально отдельно от агрегатов. Экспорт по умолчанию
не содержит прозы, комментариев, ключей или содержимого профиля; идентификаторы
и metadata дополнительно проверяются перед внешней передачей. Правила из
комментариев автоматически не активируются.

| 2 | #36–37 | Этап 1 | Различимые переносимые skills и общий verifier |
| 3 | #33, #39, #32 | Проверенный контекст этапа 2 | Целевая правка, покрытие и редакторский список |
| 4 | #27–28, затем #30–31 и дополнения #29 | Существующий quick-v1; новый контракт происхождения | Совместимый локальный клиент, отчёт и готовый план художественного опыта |

Агентская проверка не подменяет Ink Duel, а Ink Duel не подтверждает активацию
skill. Реальная проверка прозы начинается после фиксации кандидата, версий,
экспортов и отдельного разрешения запуска. Для подготовки релиза достаточно
реализовать средства, проверить их на синтетике и честно обозначить результаты
фактически выполненной агентской приёмки.

## Приёмка релиза

| Область | Минимальная проверка | Условие успеха |
| --- | --- | --- |
| Экспорт и установка | Оба агента, правильный/неправильный host, запрет, context/lock tamper, имя, отсутствующий ресурс | Валидный пакет либо отказ до публикации каталога |
| Перенос | Только папка skill, Python без engine/source и без сети | Проверка целостности и host работает; границы покрытия явны |
| Сосуществование | Два синтетических профиля в user и project; явный и автоматический выбор | Источник различим, известные совпадения диагностированы; выбор наблюдаем |
| Редактура | Четыре сценария #33 | Исходник сохранён, границы правки и ограничения соблюдены |
| Покрытие | Human-review-only, смешанный pack, отсутствующие character spans, word budget | Нет выдуманного PASS; нужные механические проверки выполнены |
| Редакторский список | RU/EN, два регистра, narrator/character, исключённое правило, испорченный context | Только применённые human_review пункты, воспроизводимость, отдельные заметки |
| План дуэлей | 30 исходников и 10 условий; меньший бюджет; повторы ID/содержимого; невыполнимые квоты | Не больше бюджета, источник один раз, воспроизводимый план и честное покрытие |
| Клиент | Пять кнопок, пустые комментарии, reload, импорт, двойной commit, клавиатура и мобильная ширина | Один голос завершает раунд; прогресс и привязки комментариев сохранены |
| Происхождение | Источник без показа ORIGINAL; показ ORIGINAL; новая сцена; legacy без task kind | Верная классификация, отсутствие утечки mapping, явная неизвестность legacy |
| Частичный отчёт | Неравные показы, повторы исторических источников, draft и неподдержанные пары | Счёт из raw votes, верные знаменатели и отсутствие выдуманного рейтинга |
| Смысл комментариев | «Оба тяжёлые, этот понятнее»; ничья с критикой обоих; одна заметка на двух карточках; общее слово | Нет вывода об абсолютном одобрении или автоматического правила |
| Новые правила | Парные случаи вмешательства/сохранения #40 | Ожидания и допустимые альтернативы готовы; поведение измеряется отдельно |
| Совместимость | Voice/context v1/v2, consumer bundle и legacy numeric/pair/multi/quick | Старые файлы читаются с исходной семантикой и не переписываются |

Обычные автоматические проверки используют только оригинальные синтетические
fixtures. Требуются Python suite, все поставляемые Node-клиенты, включая
`tests/quick_client.cjs`, сборка wheel/sdist и аудит исходников и фактических
архивов через `scripts/audit_public.py`. CI должен включить новый клиент,
ресурсы verifier и актуальные имена архивов версии. Платформенные пропуски
обозначаются как пропуски, включая Windows reparse/symlink проверки.

Релиз принимается, когда устранены P0, пройдены применимые проверки таблицы,
документация соответствует созданным пакетам, а отчёты различают выполненные
проверки и `NOT_RUN`. Утверждения о поддержке конкретной агентской поверхности
требуют её реального smoke-теста. Улучшение голоса и новые литературные выводы
не являются автоматическим следствием технической приёмки.
